# Fedora node ↔ OCI cluster networking

## Status

This documents the working Fedora-to-OCI networking state captured on 2026-08-11.

The Fedora machine is a Kubernetes worker and uses its WireGuard address as its
Kubernetes `InternalIP`:

| Node | Kubernetes InternalIP | Pod CIDR | OS |
|---|---|---|---|
| `node1` | `10.0.0.11` | `10.32.3.0/24` | Ubuntu 24.04.4 |
| `node2` | `10.0.0.12` | `10.32.0.0/24` | Ubuntu 24.04.4 |
| `fedora` | `10.100.0.2` | `10.32.4.0/24` | Fedora Linux 44 |

Cilium is using VXLAN. The captured Cilium MTU is `1360`, while WireGuard
uses MTU `1420`.

## Working topology

```text
Home LAN
192.168.0.0/24
       |
       | Fedora enp2s0 = 192.168.0.122
       |
   Fedora
   wg0 = 10.100.0.2/24
       |
       | WireGuard
       |
   node1
   wg0 = 10.100.0.1/24
       |
       +---------------- OCI VCN 10.0.0.0/24
       |       node1 = 10.0.0.11
       |       node2 = 10.0.0.12
       |
       +---------------- Kubernetes pod network 10.32.0.0/16
```

The important design point is that Kubernetes/Cilium sees Fedora as
`10.100.0.2`, rather than `192.168.0.122`. This makes the WireGuard address
the node-to-node address used by Kubernetes.

## WireGuard

Fedora's `wg0` is:

- address: `10.100.0.2/24`
- MTU: `1420`
- peer: OCI `node1`
- peer endpoint: `150.136.96.130:51820`
- persistent keepalive: `25`
- AllowedIPs:
  - `10.100.0.0/24`
  - `10.32.0.0/16`
  - `10.0.0.0/24`

The captured configuration contains a redacted private key. The example in
`networking/fedora/wg0.conf.example` intentionally leaves that key out.

## Fedora routing

The important routes are:

```text
10.0.0.0/24       dev wg0
10.32.0.0/16      dev wg0
10.100.0.0/24     dev wg0
192.168.0.0/24    dev enp2s0
```

Cilium additionally installs the per-node pod routes through `cilium_host`.

## Kernel parameters

The working Fedora state has:

```text
net.ipv4.ip_forward = 1
net.ipv4.conf.all.rp_filter = 0
net.ipv4.conf.default.rp_filter = 0
```

These are persistent configuration requirements and are represented in
`networking/fedora/99-kubernetes-wireguard.conf`.

## Firewall / iptables

The captured Fedora rules contain several Cilium/Kubernetes-generated chains.
Those chains should **not** be copied into version-controlled configuration:
they are dynamic and are regenerated by Cilium/Kubernetes.

The relevant manually-added networking behavior is:

- allow Cilium VXLAN UDP/8472;
- allow Geneve UDP/6081 if needed by Cilium configuration;
- allow forwarding between `enp2s0` and `wg0`;
- allow forwarding to/from `wg0`;
- masquerade traffic leaving through `wg0`.

`networking/fedora/iptables-wireguard.rules` contains the small, reusable
subset rather than the complete `iptables-save` output.

The captured system also has a TCP MSS clamp on forwarded SYN packets:

```text
-A FORWARD -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu
```

## Kubernetes node IP

A temporary test used:

```bash
kubectl patch node fedora --subresource=status --type=merge \
  -p '{"status":{"addresses":[{"address":"10.100.0.2","type":"InternalIP"}]}}'
```

That patch is not persistent.

The persistent configuration is to make kubelet advertise:

```text
--node-ip=10.100.0.2
```

The captured notes identify `/etc/sysconfig/kubelet` and
`/var/lib/kubelet/kubeadm-flags.env` as the relevant Fedora configuration
locations. See `networking/fedora/kubelet-node-ip.env.example`.

After changing kubelet configuration:

```bash
sudo systemctl daemon-reload
sudo systemctl restart kubelet
```

Do not blindly replace an existing kubeadm-generated flags file; merge the
`--node-ip` option with the existing arguments.

## Cilium

The captured working state has:

```yaml
mtu: 1360
devices: "enp2s0"
directRoutingDevice: "enp2s0"
```

This is worth documenting carefully: the Kubernetes node address is
`10.100.0.2`, and the host has a `wg0` route to the OCI networks, but the
captured Cilium configuration still specifies `enp2s0` as its device/direct
routing device.

Do not change this to `wg0` solely because the node's Kubernetes address is
`10.100.0.2`. The earlier troubleshooting notes considered `wg0` device
selection, but the captured working configuration uses `enp2s0`.

The Cilium node object confirms:

```yaml
spec:
  addresses:
    - ip: 10.100.0.2
      type: InternalIP
    - ip: 10.32.4.233
      type: CiliumInternalIP
  ipam:
    podCIDRs:
      - 10.32.4.0/24
```

## OCI VCN routing

The OCI route table attached to the cluster subnet contains these relevant
destinations:

| Destination | Description |
|---|---|
| `10.100.0.0/24` | WireGuard network |
| `192.168.0.0/24` | `wireguard` |
| `10.32.0.0/16` | `wireguard pod to pod communication` |

The source capture does not include the route targets/next-hop IPs in the
route-table query, so this documentation deliberately does not invent them.
The OCI console/CLI should be treated as the authoritative source for the
target of each rule.

See `networking/oci/route-rules.md`.

## OCI security-list considerations

The captured security list includes rules allowing traffic related to:

- WireGuard UDP/51820;
- traffic from `10.0.0.0/16` described as `wireguard - traffic from node2 to wg`;
- traffic from `10.100.0.0/24` described as `pod to pod connection`;
- Kubernetes ICMP testing.

The security list also contains older/testing rules. They should not all be
treated as required by the final architecture. We will Review and minimize them after
the working path has been stable for a while.

## Verification

### 1. WireGuard

```bash
sudo wg show
```

Verify a recent handshake and traffic counters.

### 2. Fedora node address

```bash
kubectl get nodes -o wide
```

Expected:

```text
fedora   Ready   ...   10.100.0.2   ...
```

### 3. Cilium node

```bash
kubectl get ciliumnode fedora -o yaml
```

Expected:

```text
InternalIP:       10.100.0.2
CiliumInternalIP: 10.32.4.233
PodCIDR:          10.32.4.0/24
```

### 4. Routes

On Fedora:

```bash
ip route
```

Verify that `10.0.0.0/24` and `10.32.0.0/16` use `wg0`.

On `node2`, verify:

```text
10.100.0.0/24 via 10.0.0.11
10.100.0.2   via 10.0.0.11
192.168.0.0/24 via 10.0.0.11
```

### 5. Pod-to-pod test

The captured successful test used two pods:

```text
test-fedora  -> scheduled on fedora
test-oci     -> scheduled on node2
```

The important acceptance criterion is bidirectional connectivity:

```text
test-fedora -> test-oci
test-oci    -> test-fedora
```

Both directions were working in the captured final state.
